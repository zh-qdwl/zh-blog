起因很朴素：压个图、拼张长图、把发票上的字抠出来——这些事一年要做上几十次，但为每一件装一个小程序太重了，用完就想删。

于是我把这些高频动作收进了一个小程序：**昊玉工具箱**。目标只有一句话——**打开即用，用完带走成果**。

## 首发的六个工具

| 工具 | 做什么 | 怎么实现 |
|---|---|---|
| OCR 图片转文字 | 拍照/选图 → 识别印刷体 → 文字可复制 | 云函数代理百度 OCR |
| 图片压缩 / 格式转换 | 调质量或尺寸 → 导出，JPG ⇄ PNG | 纯前端 Canvas |
| 拼图 / 长图拼接 | 多图竖拼 / 横拼 / 网格 | 纯前端 Canvas |
| 二维码生成 | 文本转码，也能反向扫码解码 | 本地 QR 库 |
| 简历制作 | 简约 / 双语 / 黑白 三套 Word 模板 | 云存储直接下载 |
| 图片加水印 | 文字或图片水印，可拖拽定位，实时预览 | 纯前端 Canvas |

每个工具的结果都统一支持「保存到相册 / 复制」。这一条看着不起眼，但它决定了整个产品的手感：工具类小程序最怕的是**做完了东西却带不走**。

首页会按你本地的使用次数动态排出「常用工具」前五——这个统计**只存在你自己手机上，不上传**。

## 三条自我约束

做的过程中给自己立了三条规矩，回头看，它们比功能清单更重要。

### 一、只允许一个工具走 API

六个工具里，只有 OCR 需要调外部服务，其余全部在端上用 Canvas 算完。

这不是偷懒，是刻意的：每多一个 API 就多一份成本、多一个故障点、多一处密钥要保管。招牌工具有一个就够了，其余的能在本地算就在本地算——用户不用等网络，我不用付账单。

OCR 的密钥走微信云开发的云函数，**只存在云函数的环境变量里，前端代码里一个字符都没有**。仓库里只有一份 `.env.example` 占位。

### 二、不编造数字

首页有个「当前在线人数」的胶囊。它是真的——`presence` 云函数按设备心跳去重，统计近 5 分钟活跃数。

关键在于：**云函数没部署或者断网时，这个胶囊直接不显示**，而不是退回到一个随机数或者写死的 "1024 人在线"。

这种地方一旦开始编，产品里所有的数字就都不可信了。宁可少一个胶囊。

### 三、广告默认全关

结果页的 Banner 和 OCR 的激励视频都做好了，但开关在云数据库里，**达标前默认全部关闭**。

流量主要累计 UV 到一千才能开通，在那之前挂广告位只会拖慢加载、恶心用户，一分钱也赚不到。功能先写好，等真到那天改一个字段就行。

## 「个人主体」是一道硬边界

这是我做之前没预料到的：**注册主体的类型直接决定了产品能长成什么样。**

个人主体不能开通虚拟支付，所以 v1 做不了付费会员和内购，变现只能靠广告；不能做 AI 问答类的"深度合成"小程序；不碰金融理财；再加上微信官方规范禁止测算类（算命、星座、占卜）、禁止做小程序导航和互推排行榜、禁止诱导分享。

这些约束一条条划掉之后，剩下的空间反而清楚了：**做纯粹的工具，靠好用留住人**。

至于方向，我采取的是"先通用起步"：六个工具刻意跨了不同人群，等后台埋点跑一段时间，看哪类人真的沉淀下来，再往那个方向收窄加深。埋点只有三个事件——进入工具、开始使用、导出成果，够回答"谁在用、用到哪一步"就行。

## 怎么保证它不出错

小程序没有 DOM，测试是个麻烦事。我的做法是**把纯逻辑从界面里抽出来**：尺寸计算、拼图布局、输入校验、OCR 结果解析、水印几何、内容安全解析、埋点、广告配置——这些全是不依赖 `wx` API 的纯函数，放进 `utils/`，用 Jest 直接在 Node 里测，目前 13 个 suite、44 个用例。

剩下的 Canvas 绘制和界面主流程测不了，就老老实实在开发者工具和真机上跑。**分不清哪些能自动测、哪些只能手动验，是这类项目最容易翻车的地方。**

UI 这边单独写了一份 `DESIGN.md` 作为唯一事实来源：颜色、间距、字号、动效时长全部令牌化，改界面前先读它。这份文档是被坑出来的——早期出过"白色图标压在浅玫红底盘上几乎看不见"的 bug，之后就在文档里写死了规则：**图标底盘用浅色，图标本身用对应主色，绝不把浅色前景压在浅色底上**。

顺带一提，全站动效都尊重系统的「减少动态效果」设置。
